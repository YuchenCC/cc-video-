# Safe Output 组件介绍 Voiceover

> 目标时长：约 4 分钟
>
> 播放语速：1.1 倍
>
> 口播字数：约 1200 字

## 综述

这是一个 Java 通用信息脱敏组件。

在复杂的存量代码中，敏感字段可能出现在接口、日志和跨系统调用里。依靠人工逐个排查，工作量大，也很容易遗漏。

接入组件后，不需要在大量业务代码中分别添加处理逻辑，就可以统一覆盖接口响应、日志输出和主动脱敏。组件还会记录脱敏情况，帮助程序员补充规则。

## 接入篇

接入方式很简单。

对于使用 Spring Boot 的项目，只需要引入组件依赖，再完成少量配置，就可以开启接口脱敏。不需要逐个修改 Controller，也不需要改变原有的返回对象。

如果需要处理日志，只需要调整日志输出格式。对于导出、消息发送等特殊场景，也可以在业务代码中主动调用脱敏服务。

无论从哪个入口使用，背后执行的都是同一套脱敏规则，避免同一个字段在不同场景下出现不同的处理结果。

## 配置篇

配置分为四个层次。

基础能力内置常见字段规则，可以直接处理手机号、证件号、银行卡号、邮箱和密码。

增强能力通过注解、字段和路径规则，处理命名不统一或层级复杂的数据。

例外能力允许指定字段或接口保留原值，同时记录这些例外，方便后续复盘。

自定义能力允许业务扩展特殊数据类型的脱敏策略，并复用统一的规则和统计能力。

## 日志篇

对程序员来说，日志往往是最难治理的地方。

日志里的数据，不一定是当前系统产生的。上游传入的参数、下游返回的内容，都可能在排查问题时被直接打印。只靠人工梳理，很难保证没有遗漏。

如果日志里带有明确的字段名，就直接复用接口脱敏的配置。同一个字段，不管出现在接口还是日志中，执行的都是同一条规则。

但有些日志只有一整段文本，没有字段名。这个时候，就需要兜底脱敏。组件会识别手机号、证件号和邮箱这类特征比较明确的信息，避免它们以原文写进日志。

兜底不是全量扫描，只处理边界明确的数据类型，尽量控制对日志性能的影响。

## 治理篇

可配置的脱敏工具其实并不少。只要告诉工具哪个字段是手机号、哪个字段是证件号，它就能按照规则完成处理。

难点在于，这些字段要靠谁来找。

面对一个运行多年的系统，程序员要翻接口、查对象、搜日志，还要考虑上下游传进来的数据。代码越复杂，这份清单就越难整理。好不容易排查一遍，后面增加了接口或者字段，还得重新再查。

因此，组件接入以后，排查工作并没有停止。它会根据实际运行情况，把触发兜底的日志字段、经常命中敏感信息的接口，以及主动忽略的字段记录下来。

程序员可以在报告里看到这些线索。组件也会给出建议：可能漏了哪个字段、适合使用哪种脱敏方式，以及配置可以怎么写。确认没有问题，再把它补进正式配置。

这就形成了一个循环：系统先运行，组件帮忙找漏项，程序员确认并补充配置，然后继续观察。需要说明的是，报告只记录字段、接口和命中次数，不保存敏感原文。

## AI 工程化

最后，介绍这个项目如何借助 AI 完成研发。

项目经历了多轮版本迭代，每个版本都必须按预期形成可验证的交付。

开发前，先把需求拆分为具体任务。每完成一项，都要有对应的代码、测试和文档。当前进度和剩余工作，可以直接对照检查。

代码完成并不代表研发结束。还要运行自动化测试，再把组件接入演示项目，实际验证接口、日志和报告是否按预期工作。

兼容存量技术栈、异常时不影响业务、不保存敏感原文等要求，会持续保留在项目记录中。无论后续迭代多少轮，都要重新检查。

最终，让研发过程可追踪、交付成果可运行、质量结果可验证。

这就是我们研发的 Java 信息脱敏组件，一个高质量的纯 AI 工程。它源于真实痛点，研发流程可复制，交付完整，并具备复用价值。
